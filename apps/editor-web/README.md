# Manifest — éditeur de qualification

Même entrée React et même configuration Puck pour le diagnostic navigateur et la vue MCP. Un Snapshot partagé décrit une page et un Hero ; aucun arbre de données parallèle n'est persisté.

## Flux de suggestion

La description reste temporaire et n'est pas enregistrée dans le Snapshot. Chaque nouvelle saisie remet à zéro un délai de **1 500 ms**. Hors composition IME, Manifest analyse automatiquement une fois la pause écoulée ; l'ancienne analyse n'est plus cliquable pendant ce délai. Les règles locales reconnaissent quelques choix de couleur, l'animation disponible et les lignes explicites « Titre : » / « Texte : ». Le premier motif catalogue reconnu, « ventes + nuages », propose aussi une page complète avec menu, nuages, mouvements et graphiques synthétiques. Le type de graphique, la palette coucher de soleil et la vitesse d'animation peuvent être précisés dans le même brief. Cette recette ne connecte pas un vrai rapport de ventes et n'invente pas de composition pour une demande qu'elle ne reconnaît pas.

Dans une vue MCP, `get_provider_registry` fournit uniquement les fournisseurs et modèles publics configurés par le serveur. Si un seul fournisseur et un seul modèle sont configurés, Manifest les sélectionne automatiquement ; si le registre est ambigu, l'utilisateur choisit les deux explicitement. Après **1,5 seconde** sans frappe et hors composition IME, l'éditeur envoie automatiquement l'intention et le brouillon enregistré à `start_suggestion`, suit le job et lit une proposition structurée. Sans modèle choisi, les règles locales suivent le même délai et mettent à jour une projection temporaire uniquement pour les opérations reconnues. Une nouvelle frappe retire immédiatement le candidat temporaire précédent et redémarre le délai. Le bouton « Proposer maintenant » reste disponible pour demander une analyse immédiate ; pendant un job de modèle, il permet de l'annuler. Les requêtes peuvent être facturées par le fournisseur ; dans ChatGPT, l'accès à l'API n'est pas fourni par l'inférence de l'abonnement. M0 ne met pas en œuvre de plafond de dépenses : configurer un budget côté fournisseur ou hôte avant tout essai réel. La vue ne reçoit ni clé, ni endpoint privé, ni valeur dérivée d'un secret. Le navigateur autonome n'appelle aucun fournisseur.

Une proposition de modèle est projetée temporairement et prévisualisée en lecture seule. « Conserver » appelle `keep_proposal` : le serveur vérifie la version, applique les opérations M0 dans une commande idempotente et retourne la nouvelle version. « Ignorer » rejette le candidat sans modifier le Snapshot. Si l'intention ou le brouillon change, il devient non applicable. Un changement de fournisseur vers les règles locales efface l'ancien candidat modèle afin qu'il ne masque pas une piste locale. Les jobs sont isolés entre sessions. Les règles locales se limitent à leurs indications explicites et validées ; une phrase non reconnue ne change pas la page.

Les modifications manuelles sont enregistrées après 900 ms d'inactivité ; le bouton « Enregistrer le brouillon » reste disponible. Les conflits bloquent la génération et la sauvegarde automatique, sans remplacer les réglages ouverts. « Rapport & version » sépare le brouillon enregistré, les réglages de travail et le candidat prévisualisé. Son JSON transmet les opérations et les identifiants non sensibles du modèle, jamais de credential. Il ne prétend ni approuver une révision ni exporter du code.

## Hôte et persistance

Dans une iframe d'hôte, ou avec `?host=mcp` pour un harness, le SDK MCP Apps établit la connexion puis appelle les outils `read_project`, `commit_commands` et, si le runtime est configuré, les outils de suggestion réservés à la vue. Les handlers sont installés avant `connect`. Une erreur de connexion n'active jamais silencieusement le diagnostic navigateur.

Le diagnostic navigateur conserve un brouillon local sept jours uniquement si localStorage et Web Locks sont disponibles. Sans verrou inter-onglets, l'atelier reste en mémoire pour la session. Après expiration, le document reste intact et doit être repris explicitement. Les reçus de replay sont limités à 1 000 par instance et ne survivent pas à une réouverture ; le CAS empêche le replay d'une ancienne version.

Le runtime distant compatible est facultatif et se configure hors Git avec `MANIFEST_PROVIDER`, `MANIFEST_MODEL`, `MANIFEST_API_BASE_URL` et `MANIFEST_API_KEY`. Les quatre variables sont nécessaires. Les valeurs acceptées pour le protocole disponible sont `openai`, `deepseek` et `custom`. Le détail d'exploitation est dans [services/api/README.md](../../services/api/README.md). Les mises à jour MCP ne déclenchent pas elles-mêmes l'inférence du modèle hôte ; `/validate` utilise une transmission explicite lorsqu'elle est disponible. Aucun appel réel n'est requis par les tests par défaut.

## Conception et implémentation

La coque suit la direction validée : atelier sombre, description à gauche, page claire au centre, suggestions et réglages à droite. Sur téléphone, ces zones se sélectionnent par boutons. Le thème de la page reste indépendant de la coque. `DESIGN.md` génère les variables CSS de l'éditeur ; les couleurs du site viennent du Snapshot. Les listes fournisseur/modèle sont des `<select>` natifs, choix enregistré dans la carte canonique UX.

La frontière Puck emploie les types Config/Data de la bibliothèque. Le reste du projet conserve les types Snapshot, HeroProps et commandes partagés. Les opérations de modèle sont validées contre le contrat M0 avant conservation ; aucun HTML, callback, asset externe ou code de modèle n'est exécuté. Chaque projet lu depuis le stockage ou reçu par MCP est contrôlé par recalcul SHA-256.

Le bundle singlefile de qualification contient l'éditeur complet. Son poids doit être mesuré et optimisé avant M1. La connexion dans le vrai ChatGPT, le comportement du bridge, les appels à un fournisseur configuré et la persistance de production restent à qualifier séparément.
